#+title: Future work

This file sketches directions the project could grow to demonstrate more
 patterns commonly needed when evolving a real-world API server.
None of these are commitments, they serve as a shared reference for what to
 tackle next and what patterns each direction would showcase.
Once features are implemented make sure to remove the task and document it
 elsewhere as you see fit.


* Related resource (e.g. posts with ownership)
Demonstrates:
- New migration with a foreign key referencing ~users.id~
- Diesel model with ~belongs_to~ association
- Nested routes (~/users/:id/posts~)
- Full lifecycle: migration → model → route → handler → test → doc


* Pagination on the users collection
Demonstrates:
- Evolving an existing endpoint without breaking changes
- ~?page~ / ~?per_page~ query parameters
- Diesel ~OFFSET~/~LIMIT~ (or keyset pagination for larger datasets)
- Returning pagination metadata (~total~, ~next~, ~prev~)


* Background job (e.g. periodic health report)
Demonstrates:
- Tokio tasks alongside the HTTP server
- The async runtime outside a request context


* Authentication via Keycloak (OIDC/OAuth2)
  Replace the raw ~/users~ CRUD with a real login flow backed by Keycloak.

  Prerequisites:
  - Add Keycloak to the devenv services (shares the Postgres instance)
  - Set up a Keycloak realm and client for the API

  Demonstrates:
  - OIDC discovery and JWKS verification in axum middleware
  - Guarding routes with a ~RequireAuth~ extractor (or similar)
  - Extracting identity claims (sub, email, roles) from the access token
  - Mapping Keycloak users to local ~users~ rows (upsert on first login)
  - Replacing the raw user CRUD with self-service ~GET /users/me~ and ~PATCH /users/me~ endpoints (read and edit own profile)
  - Integration test that obtains a real token from Keycloak
