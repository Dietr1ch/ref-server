#+title: Future work

This file sketches directions the project could grow to demonstrate more
 patterns commonly needed when evolving a real-world API server.
None of these are commitments, they serve as a shared reference for what to
 tackle next and what patterns each direction would showcase.
Once features are implemented make sure to remove the task and document it
 elsewhere as you see fit.


* Pagination on the users collection
Demonstrates:
- Evolving an existing endpoint without breaking changes
- ~?page~ / ~?per_page~ query parameters
- Diesel ~OFFSET~/~LIMIT~ (or keyset pagination for larger datasets)
- Returning pagination metadata (~total~, ~next~, ~prev~)


* Background job (e.g. periodic health report)
Demonstrates:
- Tokio tasks alongside the HTTP server
- The async runtime outside a request context


* Authentication
** Alternatives
*** Custom
- ~allowthem~ :: This library is specifically designed for this use case, with
   an "embedded" mode where it manages authentication tables directly in your
   application's database. You add it as a dependency, pass your database pool,
   and it provides a AuthClient trait for registration, login, and session
   management directly within your app. It supports email/password, OAuth2 login
   (Google, GitHub), and TOTP-based MFA.
- ~axum-oidc-client~ :: If you want to use an existing external identity
   provider (like Google, GitHub, or a corporate provider) but want to skip the
   overhead of running your own full service, this is a strong choice. It's a
   middleware library that handles the OAuth2/OIDC protocol with PKCE, automatic
   token refresh, and provides type-safe extractors for authenticated users.
- ~sa-token-rust~ :: This is a comprehensive authentication and authorization
   framework with specific sa-token-plugin-axum support. It offers a wide array
   of features, including fine-grained RBAC, distributed session management, and
   SSO capabilities.
- ~auth-framework~ :: Marketed as a complete client and server solution, this
   framework provides OAuth 2.0 authorization server capabilities, OIDC

*** Rely on Keycloak (OIDC/OAuth2)
  Demonstrates:
  - OIDC discovery and JWKS verification in axum middleware
  - Guarding routes with a ~RequireAuth~ extractor (or similar)
  - Extracting identity claims (sub, email, roles) from the access token
  - Mapping Keycloak users to local ~users~ rows (upsert on first login)
  - Replacing the raw user CRUD with self-service ~GET /users/me~ and ~PATCH /users/me~ endpoints (read and edit own profile)
  - Integration test that obtains a real token from Keycloak
